Maimai personal app API (all requests same origin)

Production uses HTTPS and one Master Key. POST /api/auth/login {master_key} creates
a Secure, HttpOnly session cookie; GET /api/auth/session reports authentication;
POST /api/auth/logout revokes the session. Personal APIs require authentication.

GET /api/health -> {ok, catalog_charts, imported_charts}
GET /api/venues/summary -> {levels,items,totals,total,pending_count}
  Rows contain exact venue name, city, counts by current catalog level and total AP.
  Columns are 12+, 13, 13+, 14 and combined 14+/15; other levels add an explicit
  "other" column so the totals never silently omit a confirmed venue-associated AP.
  Pending claims are counted separately and do not replace the previous confirmed venue.
  This summary does not inherit the AP page's default constant range. Cache-Control: no-store.
GET /api/catalog/update -> catalog updater status, current snapshot and last result
GET /api/catalog/update/report -> {diff,issues,sources,source_policy} from the active snapshot
  Reads catalog_diff.json, build_report.json and raw/sources.json on demand.
  source_policy records the authority rules used to build that snapshot; old snapshots
  without it return null, never the current program's policy as a historical claim.
  Missing diff/issues/sources default to {}, [] and []; Cache-Control: no-store.
POST /api/catalog/update -> HTTP 202, starts the catalog update job
POST /api/catalog/remy/retry -> HTTP 202, retries Japanese chart-release research
  No request body. A concurrent job returns HTTP 409; invalid operation -> HTTP 422.
  Jobs are owned by app.state.catalog_updates and closed on application shutdown.
  Public catalog updates do not replace the personal SQLite database.
GET /api/catalog/data -> active catalog.json, Cache-Control: no-store
GET /api/summary?group=all|low|high|catalog
  -> {total,complete,ap,remaining,conflicts,legacy_complete,groups:{low,high,catalog},
      levels:[{level,total,complete,ap,remaining,conflicts}],
      constants:[{constant,total,complete,ap,remaining,conflicts}],sync,import_info}
  Default summary totals include every current non-Utage catalog chart, including
  newly added charts outside the original TSV. import_info remains the import receipt.
  Accepts the same q, difficulty, type, status, constant_min, constant_max, level,
  venue and version filters as /api/charts. Totals, levels and constants reflect all
  active filters; groups remain the unfiltered global group counts.
GET /api/chart-filters?group=all|low|high|catalog
  -> {levels:[string],constants:[number],versions:[{value:string,label:string}]}
  Options cover the full group regardless of active chart filters. Levels/constants
  sort ascending; versions sort chronologically with unknown last.
GET /api/charts?q=&group=all|low|high|catalog&difficulty=0..4&type=standard|dx
  &status=all|complete|incomplete|ap|legacy|conflict&constant_min=&constant_max=
  &level=&venue=&version=&offset=0&limit=100&sort=constant_desc|constant_asc|title
  -> {items:[Chart],total,offset,limit}
  Default and group=catalog lists include all non-Utage catalog charts. low/high are
  internal legacy-source filters, not separate libraries in the frontend.
  Constant sorts use numeric song_id ascending as the first tiebreaker, then type,
  difficulty_index and chart_key. Default is constant descending.
  Version values use only the final jp_release_version, shared with the cover UI.
  No SEGA/CN fallback. Missing JP versions match __unknown__ (版本待核实).
  Catalog conflicts withhold the entire chart. Only admitted charts are returned.
  Persisted field choices survive future source changes until explicitly revoked.
  PLUS versions remain distinct. Set constant_min=constant_max for an exact constant.
GET /api/charts/{chart_key} -> Chart
GET /api/ap-records -> {items:[{chart_key,title,type,difficulty_name,constant,
  jacket_url,thumbnail_url,record_revision,pending_record}],count}
PUT /api/charts/{chart_key}/ap-record {venue,request_id,expected_revision}
  -> {chart:Chart}. Saves a pending venue claim, never marks a chart AP by itself.
  request_id is a client-generated idempotency key. Replaying the same request
  does not recreate a subsequently cancelled/confirmed claim. A different payload
  cannot reuse its key. Stale revisions return 409 without overwriting newer work.
  A required venue must already exist; creation is only available in My Venues.
  Charts with a recorded venue cannot create or edit a pending claim. Sync also
  cannot replace a recorded venue with a previously queued correction.
DELETE /api/charts/{chart_key}/ap-record?expected_revision=N -> {chart}
  Cancels only the pending claim; previous AP evidence and confirmed venue survive.
GET /api/venues -> {items:[{name,count,last_used_at}]}
  Includes recent pending venue choices; count includes only completed charts.
GET /api/venues/map -> {items:[{name,city,total,pending_count,location,jackets}]}
  location is null or {latitude,longitude,coordinate_system,updated_at}.
  All API coordinates are WGS84. Pre-existing unlocated venues retain null
  coordinates. A location edit never renames or reassigns AP records.
  jackets contains at most three confirmed AP charts per venue, with chart_key,
  title,jacket_url,thumbnail_url,difficulty,difficulty_name,level,constant,status,
  type,achievement. No pending claim counts as a completed AP.
GET /api/venues/charts?name=&offset=0&limit=60 -> {items:[Chart],total,offset,limit}
  Exact venue match, confirmed AP only; max limit 100. Sort by current constant
  descending, then ID and difficulty ascending. Only the requested page is returned.
PUT /api/venues/location {name,latitude,longitude}
  -> {name,location}. Saves directly and can create a new named venue.
  name is the display name. Both coordinates are required, finite and in range.
  Only the name, point and update timestamp are stored. No AP state is modified.
GET /api/venues/search?q=&city= -> {items,provider,attribution,attribution_url}
  Explicit user search only; no autocomplete or automatic background requests.
  Default provider is Photon https://photon.komoot.io/api/. MAIMAI_GEOCODER_URL
  can select another Photon endpoint or disable lookup with an empty value.
  Results contain a transient place_name/address label and WGS84 coordinates.
  The labels are not stored on the venue. Results
  are cached for 7 days (at most 512 queries). Uncached requests are limited to
  one per second across app workers. HTTP timeouts and safe error messages keep
  provider errors separate from direct map selection. Display attribution.
  All venue map/location APIs require the existing session and use no-store.
GET /api/settings/divingfish -> {configured,source:"environment"|"local"|null,sync}
PUT /api/settings/divingfish {token:"Import-Token"} -> same public settings.
  Empty token clears local saved token. Token is never returned or logged.
GET /api/sync/status -> {job,divingfish}
  divingfish={configured,last_sync}. last_sync is the latest successful receipt or null.
  job=null or {id,kind:"divingfish",state,stage,message,error,result}; state is
  running, succeeded or failed; stage is fetching, validating, completed or failed.
  error is null or {code,message}. No token is exposed.
POST /api/sync/divingfish (no body) -> HTTP 202, job object
  Manual only; there is no scheduled pull. Requires a saved Import-Token (409 no_token).
  Reads the complete /player/records with the Import-Token header, 30 s timeout,
  no redirects. The eligible pending IDs/revisions are captured at job start. Only
  unchanged claims whose latest complete response has fc=ap/app promote their venues.
  An AP without a claim still counts as AP and reports venue_pending when a venue is
  required. Observed AP evidence is never revoked by a later missing or lower record.
  Scores, evidence, venue confirmations and receipt commit together; a malformed or
  failed response leaves all personal data untouched. Changing the token during the
  request discards the response (token_changed).
  Receipt={ok,source:"divingfish",records,matched,unmatched,synced_at,sync_id,confirmed,
  pending,conflicts,venue_pending}.
  Jobs share a nonblocking process/file lease (busy -> 409); starts have a short
  cooldown (429). The UI polls status.
Chart fields:
id, difficulty, chart_key (id:difficulty), lxns_song_id, song_id (alias of id),
title, display_title, artist, type, difficulty_index (alias of difficulty),
difficulty_name, level, constant, divingfish_id, jacket_url, thumbnail_url,
jp_release_version, jp_release_version_candidate, release_status,
group(low/high/catalog), in_original_table, requires_venue, legacy_complete, legacy_venue,
manual_ap(null/true/false), manual_venue, venue, note, manual_date,
achievement(null or number, explicit manual score preferred),
provider_achievement, provider_fc, provider_synced_at, provider_source(divingfish/null; older rows may show wahlap),
provider_fs, provider_dx_score, provider_rate, provider_ra,
pending_record(null or {id,venue,created_at,updated_at,revision,reason}),
record_revision, venue_pending, ap_confirmed_at, venue_confirmed_at,
is_ap, is_complete, status(app/ap/legacy/incomplete), conflict, warnings.
Legacy completion is distinct from verified AP because original table includes deletion exemptions.
Low/high are imported directly from original TSV source. Catalog-only charts remain a separate group.
requires_venue is true for imported high charts, false for imported low charts;
catalog-only charts use constant >= 12.6. Clients use this flag for the venue field
without presenting the source groups as separate AP libraries. Existing imported
records are preserved.
Provider AP requires fc=ap/app; 100+ achievement alone never means AP.
New pending claims never contribute to completed counts, AP masks or exports.
Provider-confirmed AP counts even if a required venue is missing (venue_pending).
Confirmed AP evidence survives later missing/reduced scores; an actual non-AP
response is surfaced for review. A recorded venue cannot be replaced through a
new pending claim. Venues come only from the user's records.
score_sync_sources ties each immutable sync_id to its source; old sync history is
migrated as divingfish. Account hashes are private. Personal chart fields remain
separate from catalog metadata, and optional upload receipts never alter AP evidence.
Provider exact achievement is not auto-confirmed for covers (account score masks may apply).

GET /jackets/{song_id}.png -> active snapshot image, falling back to base catalog cache
  Numeric PNG filenames only. Private revalidation permits updated art at the same URL.
  Original resolution is retained for cover/completion exports.
GET /jackets/thumbnails/{song_id}/{revision}.webp -> authenticated 160px WebP preview
  thumbnail_url is generated from the current source asset; source changes produce a new URL.
  Private browser caching and ETag/304 are supported. Server-generated previews are bounded.
  Preview URLs do not replace jacket_url and are not used for high-resolution exports.
Personal JSON APIs and exports remain no-store. Static artwork caching never unlocks API access.
Chart reads reuse one assembled snapshot until personal writes or catalog publication change it;
transactional sync reads bypass that cache so their receipt includes the transaction's own writes.
GET / -> frontend/dist/index.html, React + TypeScript app built with Vite.

Run: ./start-app.sh (installs missing dependencies and builds the React app)
Front-end development: npm --prefix frontend run dev (API proxy to 8766)
Runtime data: backend/runtime/personal.sqlite3 (0600), secrets.json (0600).
Catalog base: data/catalog. If data/catalog/current exists, its resolved directory
provides catalog.sqlite, catalog.json and preferred jackets. Store.load_catalog(path)
preloads both read-only indexes without publishing them; install_catalog(tuple)
publishes them together. reload_catalog() follows current. Personal data stays separate.
Environment overrides: MAIMAI_RUNTIME_DIR, DIVINGFISH_IMPORT_TOKEN.
Tests use isolated temp DBs and mocked provider responses, never personal remote records.
Import source path defaults ~/Downloads; override MAIMAI_IMPORT_DIR before first startup.
The backend binds loopback behind the authenticated HTTPS deployment; see deploy/README.md.

Catalog adjudication (independent of personal AP records):
GET /api/catalog/data -> schema_version=2, charts[] (no songs[]), counts={total,admitted,pending,...}.
  Canonical ID = LXNS ID for STD/UTAGE, LXNS ID + 10000 for DX.
  Primary key = (id,difficulty). Pending chart entries are not returned here.
GET /api/catalog/records/review -> {revision,decision_revision,applied_decision_revision,
  decisions_pending,counts:{total,admitted,pending},records}
  Each record is one (id,difficulty), with only unresolved fields that have at least
  two distinct valid comparable values. Empty values and status flags are not conflicts.
  arcade-songs contributes JP versions only, never metadata/notes/designer options.
  No current/default/recommended values. Each required field must be selected.
POST /api/catalog/records/decisions/batch -> CatalogUpdateState (202)
  {base_catalog_revision,base_decision_revision,
   records:[{id,difficulty,choices:[{field_key,option_id}],note?}]}
  Submit 1-10000 charts together after previewing all choices in the confirmation dialog.
  Each included chart must submit all and only its required fields; duplicate charts
  or fields are rejected. Charts without any selection may be left for a later batch.
  All records validate against one review and one pair of base revisions before any
  writes. One atomic DB transaction saves every choice; only one rebuild is queued.
  Invalid or incomplete -> 422, stale or busy -> 409, with no partial decision writes.
  A failure in the last chart never saves the earlier charts or starts a rebuild.
  Version/date stay paired. Server resolves values/evidence from submitted option IDs.
  Selected values persist through source changes/rebuilds until explicit revoke.
  Failed publication keeps prior snapshot and saved decisions; decisions_pending=true.
POST /api/catalog/records/decisions -> CatalogUpdateState (202)
  {base_catalog_revision,base_decision_revision,id,difficulty,
   choices:[{field_key,option_id}],note?}
  Compatibility endpoint; delegates to the same batch implementation with one record.
GET /api/catalog/records/decisions -> {revision,decision_revision,decisions_pending,records}
  Independent saved manual choices, grouped by chart; includes missing-source records.
POST /api/catalog/records/decisions/revoke -> CatalogUpdateState (202)
  {base_catalog_revision,base_decision_revision,id,difficulty,field_keys?}
  Omit field_keys to revoke all fields for this chart; otherwise revoke the selected fields.
  Revocation restores comparison and may withdraw the entire chart to pending admission.
POST /api/catalog/decisions/reapply -> CatalogUpdateState (202), no network.
GET /api/catalog/decisions/history?object_key=&limit=100 -> {items:[events]}
  Events include original value, revision, timestamp and batch_id; revoke retains history.
State includes decision_revision,applied_decision_revision,decisions_pending.
Personal records for pending charts remain stored and can reattach after admission.

Bilibili post-upload organization (existing own videos only):
GET /api/bilibili/status -> {connected,account:{mid,name}|null}
POST /api/bilibili/login -> {login_id,url,expires_at}; QR authorization URL only.
GET /api/bilibili/login/{login_id} -> {state,account?}
DELETE /api/bilibili/session -> removes the locally saved Bilibili session.
GET /api/bilibili/videos?page=1
  -> {items,has_more,page,collections:[{id,title,sections:[{id,title}]}],unavailable_collections}
  Only members of the signed-in account's handplay collections named
  "maimai <level> AP" (for example maimai 13+ AP). Video titles are not filters.
  Reads complete collection membership, deduplicates, sorts newest first and then
  paginates 20 items. Incomplete upstream results fail instead of listing all uploads.
  A collection the public listing refuses (draft/under review) is skipped and named in
  unavailable_collections. Page 1 re-reads B 站; later pages reuse that snapshot for
  up to 5 minutes. Applying a publishing job clears the snapshot.
GET /api/bilibili/videos/{bvid} -> existing title, both covers and revision.
  Explicitly loading an owned BV remains available for new, uncollected handplays.
GET /api/bilibili/collections/order -> {checked_at,sections:[OrderReport]}
  Explicit read-only inspection of all owned collection sections. Each OrderReport
  has season_id, season_title, section_id, section_title, revision,
  status (ordered|changes|blocked), current, desired and unmatched.
  Order items contain episode_id, aid, bvid, title, song_title, chart_key, version
  and position. Positions are one-based; a proposed new item has episode_id=null.
  Unmatched items include bvid, aid, title and reason. Unknown identities or versions
  block multi-item sorting; empty/single-item sections require no comparison.
  Uses chart-specific JP release order, then NFKC/casefold song names; equal keys
  retain their relative order. Re:MASTER uses its own release and PLUS stays separate.
POST /api/bilibili/prepare
  {bvid,chart_key,achievement,combo,constant,section_id,mirror_horizontal?,
   title_override?,include_type?,version_override?} -> frozen plan with plan_id.
  The score is supplied explicitly for this video; a current personal best is never
  substituted. Plans expire after one hour. Existing STD/DX suffixes, Utage notation
  and the historical mirrored-title exception are preserved by default.
  Explicit chart selection saves an account-scoped BVID/chart identity binding in
  the personal database, including when another item blocks the proposed order.
  This permits several previously unrecognized videos to be associated in turn.
  Bindings retain identity evidence, not a frozen candidate release version.
  The plan also freezes order: an OrderReport with target_bvid and target_position.
  The preview includes the proposed video's position before any external writes.
  A blocked plan can be inspected but cannot be applied. Missing order information
  in an older plan requires regeneration instead of bypassing the new checks.
POST /api/bilibili/apply {plan_id,cover16,cover43} -> persistent job receipt.
  cover16 and cover43 are PNG data URLs, exactly 1920x1080 and 1440x1080.
  Rechecks ownership and the frozen revision before updating covers/title/section.
  The existing archive metadata and video files are preserved. Unsupported archive
  configurations are rejected before editing. This does not upload a new video.
  Checks the frozen section before any upload/edit, then verifies exact membership
  before reordering. Preserves section metadata and sends all episode IDs, never
  only the newly added video. A job completes only after order has been read back.
GET /api/bilibili/jobs -> recent account-owned jobs.
GET /api/bilibili/jobs/{job_id} -> job, frozen plan and saved PNGs when unfinished.
POST /api/bilibili/jobs/{job_id}/retry -> resumes with those exact saved PNGs.
  An uncertain write is read back before retrying, never blindly submitted again.
  Unresolved writes block a competing job on the same video; safely superseded jobs
  cannot retry. No external mutation occurs while listing videos or preparing a plan.
  Session credentials stay in a private runtime file, covered by encrypted backup.
  All routes require the site's authenticated session; upstream login errors do not
  invalidate that session. Error responses never include credentials or raw payloads.
